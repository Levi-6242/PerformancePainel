Arquitetura do portal Grid

Plataforma, OS Creator web e a terceira aplicação

22/09/2026 · proposta · baseada no que já roda em produção

A pergunta por trás da pergunta. "Um canto centralizado da Grid" é sobre endereço e login, não sobre repositório. O portal já existe e já engoliu duas aplicações — uma delas de outro repositório. O que falta não é juntar código: é parar de escrever o encanamento à mão a cada aplicação nova.

1O que roda hoje

Três serviços Flask, três portas, um domínio só. Para quem usa, é um lugar.

proxy HTTP — sem import entre projetos tráfego do usuário

Repare na coluna da direita: as duas aplicações resolvem identidade de jeitos diferentes. Não é descuido — é que elas precisam de coisas diferentes.

AplicaçãoPrecisa saber quem é a pessoa?Por quêComo resolve hoje
Gêmeo Não Só exibe dados. A resposta é a mesma para todo mundo. Segredo compartilhado. O serviço confia que quem chegou já passou pelo login.
OS Creator web Sim Cria OS em nome da pessoa no Fracttal. O nome dela vai na ordem. Sessão própria: cada um loga no Fracttal e o serviço guarda num cookie seu.

2O que quebra na terceira

Nada disso dói com duas aplicações. Com a terceira, três coisas passam a doer — e nenhuma delas é o repositório.

O proxy é copiado à mão

gemeo_proxy e os_web_proxy são quase idênticos: ~20 linhas cada, com diferenças reais espalhadas no meio (timeout de 30 contra 180 s, quais cabeçalhos voltam, repassar cookie ou não). A terceira vira uma terceira cópia — e a correção de um bug precisa ser lembrada em três lugares.

Cada aplicação refaz o login

A pessoa já entrou no portal. Se a terceira também precisa saber quem ela é, ou ela loga de novo, ou ganha mais um segredo compartilhado — e aí o serviço não sabe quem fez o quê. Com seis aplicações, são seis logins ou seis segredos.

O portão vira uma lista de exceções

O _auth_gate já tem seis exceções, cada uma com "gate próprio no handler": /api/campo/ por chave, /api/tickets/ por JWT do Fracttal, /api/gemeo/ pelo segredo. Cada integração nova acrescenta uma linha e uma regra que mora longe dali.

3A arquitetura proposta

Uma mudança pequena com três consequências: um proxy só, dirigido por um registro de aplicações, onde o modo de identidade é declarado — não codificado.

Os três modos, e quando usar cada um

ModoQuandoO serviço recebeExemplo
confianca A resposta é igual para todo mundo. Basta saber que passou pelo login. Um segredo compartilhado no cabeçalho. Gêmeo — hoje já é assim, não muda nada.
sessao_propria O serviço age em outro sistema com a credencial da pessoa lá. O cookie dele, repassado nos dois sentidos. OS Creator — a sessão é do Fracttal, não nossa. Continua como está.
identidade O padrão para o que vier. O serviço precisa saber quem fez, e a identidade é a do portal. Quem é a pessoa, num cabeçalho assinado pela plataforma — que já sabe, pelo login Microsoft. PCM: registra quem lançou cada apontamento sem pedir senha de novo.
Por que o terceiro modo é o que destrava a escala. A plataforma já autenticou a pessoa. Em vez de a aplicação nova refazer o login ou ganhar mais um segredo anônimo, ela recebe quem é — assinado, para não dar para forjar. A aplicação não precisa de tela de login, não guarda senha, e ainda assim sabe de quem é cada registro. É o mesmo desenho que faz o /api/campo/ e o /api/tickets/ existirem hoje, só que uma vez, com nome, em vez de uma exceção por integração.

Juntar os repositórios andaria para trás por dois motivos. O primeiro: este repositório é público desde a subida no servidor — trazer o OS Creator para cá publica a integração com o Fracttal e o fluxo de chamados. O segundo é o motivo de ele ter saído em 28/08: o código estava numa conta pessoal e só uma pessoa conseguia publicar versão. Cada área com o seu repositório é o que tira você do caminho crítico de todo mundo.

5Como chegar lá sem parar nada

Nenhum passo exige o seguinte. Dá para parar em qualquer ponto e o que já foi feito continua valendo.

  1. Agora, junto com o PCM. Unificar os dois proxies numa função dirigida pelo registro. As diferenças que hoje estão no meio do código (timeout, cabeçalhos de volta, repassar cookie) viram campos declarados por aplicação. É refatoração pura, com os testes que já existem cobrindo. O PCM entra como a primeira linha nova do registro, sem escrever proxy nenhum.
  2. Quando o PCM precisar saber quem é a pessoa. O modo identidade: a plataforma assina quem está logado e manda no cabeçalho. O gêmeo e o OS Creator não mudam — ficam nos modos que já usam.
  3. Quando a terceira aplicação estiver de pé. A Entrada vira índice de verdade: mostra o que existe e o que cada pessoa pode abrir. Hoje ela é a tela do time de Performance com um card de OS.
  4. Quando começar a incomodar. Recolher as seis exceções do _auth_gate para o mesmo registro. É higiene, não urgência — só que cada integração nova acrescenta mais uma, então quanto antes, menos tem para recolher.
O que fazer hoje: nada de arquitetura. O servidor precisa do git pull e do restart, e o oem precisa que o servidor consiga cloná-lo (é privado — deploy key ou token de leitura) e subir o os_web como segundo serviço. O passo 1 vale a pena quando o PCM chegar, porque aí ele paga a si mesmo: em vez de uma terceira cópia do proxy, uma linha no registro.
